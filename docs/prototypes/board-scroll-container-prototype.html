Why the Board lives in its own scroll container

Decided: a dedicated overflow: auto scroll container holds the 1920×1080 Board. The toolbar is a strip above it, and the Trash zone is pinned over the container's visible corner, outside the scrolling content. This page shows why, using a real layout: the picture on the left is a real browser window (an iframe) and every number on the right comes from real getBoundingClientRect() and scrollLeft reads. Each walkthrough asks you to predict first, then press the buttons to check.

Log

    Defending it live

    “The Board is a fixed 1920×1080 surface inside its own scroll container, so the toolbar and the Trash zone sit outside the thing that scrolls: they never cover the Board, never move, and a Gesture can measure both once, at press time, with getBoundingClientRect().”
    “Why not just let the page scroll?”

    The coordinate maths is identical, since getBoundingClientRect() includes scroll in both layouts (walkthrough 7). The difference is who owns the scrolling. With page scroll the toolbar must be a position: fixed overlay, so the Board slides under it: either the top strip of the Board is hidden, or you pad it and content still passes beneath. The scrollbars run the whole window height next to the toolbar. With a container, the scrollable area is exactly the Board's visible part, and nothing overlaps it except the Trash zone, which is deliberate.

    Honest concession: page scroll gets some things for free. Reload restores the scroll position (a container starts at 0,0 unless I save it), keyboard scrolling works without focus management, and there's one less element in the tree. None of these is a requirement in the brief.

    “Isn't a nested scroller bad for accessibility or trackpads?”

    It isn't nested: the body is height: 100vh; overflow: hidden, so the container is the only scroller. There's no scroll chaining and no scroll-inside-scroll trap, and wheel or trackpad input goes straight to it. I'd add overscroll-behavior: contain so a horizontal trackpad swipe at scrollLeft = 0 doesn't trigger the browser's back-swipe.

    Honest concession: a scroll container needs a little care for keyboard users. Give it tabindex="0" and an accessible name (role="region" aria-label="Board") so arrow keys and Page Down scroll it and screen readers announce it. Page scroll gets that for free.

    “Why is the Trash zone a sibling of the Board and not inside it?”

    Anything inside the scrolling content moves when it scrolls. A Gesture caches the Trash rect at press time (pointer capture stops hover events, so it has to use rectangle maths), and a cached rect for something that moves goes stale. Walkthrough 4 shows both failures: dropping on the visible Trash misses, and dropping on empty space deletes. As a sibling, the Trash's screen rect is constant for the whole Gesture.

    “What happens if the Board scrolls during a drag?”

    Say it straight: that's the open edge, scheduled for the next grilling round. Today the Note keeps its Board position because clientX deltas don't change when the content scrolls, so the Note slides away from the pointer by exactly the scroll distance (walkthrough 5). The fix options (re-read the rect on scroll, or add the scroll delta) are next round's question.
